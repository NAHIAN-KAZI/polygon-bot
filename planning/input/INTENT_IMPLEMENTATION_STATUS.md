# Intent Implementation Status

Standing tracker: for each of the bank's 14 intents, which endpoints are
actually implemented in this codebase today vs not. Companion to
`INTENT_API_READONLY_MAP.md` (GET vs mutating, same 46-endpoint source) and
`API_SCREEN_MAP.md` (which real app screen calls each endpoint) — this file
is the "did we actually build it" layer. **Update this file alongside
TASKS.md whenever a task changes an intent's coverage** — don't let it go
stale.

Legend:
- ✅ **App action (T-79)** — the bot makes no bank call; it returns `APP_ACTION` with prefill and the app shows an inline box (see `handoffs/COMMON.md` §8 and §11).
- ✅ **Done** — real adapter calls this live endpoint, wired end-to-end.
- ✅ **Done (gather+redirect)** — never calls the real (mutating) endpoint
  by design (ADR-0008: inform/redirect only) — the bot gathers details via
  clarification and returns a confirmation summary + navigation hint for
  the frontend instead.
- 🔶 **Approved, not yet built** — user has explicitly approved implementing
  this, work not started/landed yet.
- ❌ **Not done** — read-only (GET), available under current policy, simply
  not implemented yet.
- ⛔ **Blocked** — mutating (POST/PUT/PATCH/DELETE), blocked by the standing
  GET-only policy unless explicitly carved out as an exception (see below).
- 🚫 **No backend** — dead end per the bank's own doc, unusable regardless
  of policy.
- ➕ **Extra** — implemented, but not actually part of this intent's official
  endpoint list (built for a different real-world reason).

**Exceptions to the GET-only policy, explicitly approved by user:**
- Beneficiary **add** (14.20, POST) — approved 2026-10-01. Built end-to-end
  (T-60): gather nickname + account number → explicit yes/no re-confirmation
  → only then `BeneficiaryAddAdapter`. Lives under its own synthetic category
  `beneficiary_management`/`beneficiary_add` (ADR-0011 amendment, 2026-10-03 —
  it had no taxonomy home before, so it could never be classified). Unit
  tested. **Live 2026-10-03: bank returns 500** for the add (OTHER_BANK and OWN_BANK);
  waiting on the API team for the required body. Nothing was left on the account.
- Card **freeze** (4.1 / 12.2, PATCH) — approved 2026-10-01. Built end-to-end
  (T-57): list cards (GET) → ask which card if 2+ → ask reason → `OTP_REQUIRED`
  (bank's `otp/v1/send` + `otp/v1/verify` → `verificationToken`, plus
  password) → freeze. Never sends a PIN/OTP/password to the LLM or the session
  log. **Live-verified 2026-10-03**: ACTIVE → BLOCKED via chat, restored by unfreeze.
  Dev OTP accepts `0000`.
  Unfreeze itself is never routed by the bot (customer is pointed to the app).
- Raise **dispute** (2.2 / 3.3 / 8.2) — gather + redirect only (T-61): the bot
  asks what's needed, then returns a navigation hint; it never POSTs.

**Routing (T-62/T-63, 2026-10-03):** every message goes through two LLM
stages — pick a domain (accounts, deposits/loans, cards, transfers, fees,
disputes, profile, other, general), then pick the exact service from that
domain's descriptions only. No keyword lists, no hard-coded questions:
clarifying questions and replies are generated by the LLM from the real facts
the code decides (`_phrase`, `_synthesize_reply`, both number-checked against
the data). Account-scoped asks check how many accounts/cards exist and ask
"which one" when there are several; the next message is resolved against that
list (digits, frontend pick, or an LLM pick of the wording).

**Money (T-65):** the bank returns poisha everywhere except QR payment
history (taka). `*Formatted` payload fields are converted (÷100).

**Live status (2026-10-03, dev user `taslim_islamic`):** multi-turn eval 31/35;
card freeze live-verified (restored by unfreeze); beneficiary add blocked on a
bank 500. Security: payload ids can no longer be injected into bank API paths
(T-71). Cross-intent live sweep (T-73, 74 cases, all 14 intents, every message
style): 69/74, with the reply-quality bugs it found fixed (T-72 accounts balance
included).
