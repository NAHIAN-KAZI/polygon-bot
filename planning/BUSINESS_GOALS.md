## Goals (priority order)

1. **Recognize banking-service requests and return structured routing information** — so the
   main Polygon Bank application can navigate the customer to the right feature (category,
   service, subservice identified; ambiguous requests get a clarifying question, never a guess).
2. **Preserve all existing knowledge-base chat behavior and its API contract exactly as-is** —
   this extension is purely additive for the existing integration team; nothing that works today
   may regress.
3. **Establish a foundation that absorbs future change without a redesign** — customer identity
   handling, a reconfigurable service taxonomy, and a replaceable banking-service integration
   layer, ready for the bank's official taxonomy and real banking APIs once supplied.
4. **Keep the new behavior easy to verify** via the existing demo/test frontend. *(Should-have)*

## Success criteria

- A request containing only `{"text": ...}` behaves identically to today's behavior — zero
  regression for the existing integration team.
- Example banking-service utterances ("what's my balance," "I want to send money," "show my
  transactions," "pay my electricity bill," "block my card") resolve to the correct
  category/service/subservice.
- A genuinely ambiguous request ("I need help with my card") produces a clarifying question, not
  a guessed subservice.
- A banking-service request without a valid customer identity token returns a distinct,
  structured "authentication required" response — never a generic error, never silently allowed
  through.
- The structured banking-service response carries a version marker.
- Knowledge-base chat, document upload/retrieval, and the demo frontend's existing workflows all
  continue to work unmodified.

## Constraints / invariants

- The main Polygon Bank application owns its own frontend, backend, real banking APIs,
  transaction processing, and customer login/identity — none of that is built or duplicated here.
- The category/service/subservice taxonomy shipped now is a provisional placeholder; the bank's
  official taxonomy will replace it later without requiring a redesign.
- Customer identity token validation details (issuer, signing method, claims) are not yet
  available — treated as a pending, pluggable piece of the design, not a blocker.
- Real external banking-service APIs are not available yet — mock data stands in until they are.
- The existing `/chat` API contract, as documented for the current external integration team,
  must remain fully backward compatible.
- Conversation/session context may live only in the running service's memory for this phase (lost
  on restart) — a durable/shared store is deferred, not ruled out, for later.
- The LLM is never the authorization decision-maker for a banking-service request, and never the
  source of customer identity — authorization and identity always come from the backend/token,
  never from LLM-generated parameters.
